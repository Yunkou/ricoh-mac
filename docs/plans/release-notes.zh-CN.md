# GitHub Release 页面的产品说明

本文说明如何把 GitHub Release 页面改成面向普通使用者的产品说明，并规定每个版本的功能更新如何撰写。工作流尚未改动。

## 现状

当前发布说明由两部分拼接而成。

1. `scripts/release-notes-preamble.md` 提供中英双语的安装说明，并在开头强调 ad hoc 签名、未经公证，以及可用 `xattr` 清除隔离属性。SHA-256 校验值也放在这段的前部。
2. 工作流随后调用 `gh api repos/.../releases/generate-notes`。对已发布的 v0.1.0、v0.1.1 和 v0.2.0，这段通常只得到一条「Full Changelog」链接，没有产品功能说明。

因此，使用者打开 [v0.2.0 发布页](https://github.com/Yunkou/ricoh-mac/releases/tag/v0.2.0) 时，先看到签名限制和命令行校验，而看不到「照片」「设备」、本地相册、大图浏览、毛玻璃窗口或字体这些实际变化。标题也固定为 `ricoh-mac ${TAG}`，偏仓库名，而不是产品名。

## 建议的页面结构

GitHub 每个 Release 只有一份说明正文。继续在同一页中使用中文和英文，中文在前。建议顺序如下。

1. 本版本更新（中文）
2. What's new（English）
3. 安装（中文）
4. Install（English）
5. 校验（可选），中英各一句引言，校验值只出现一次

「本版本更新」只写使用者能感知的变化，使用产品用语。不要列出提交标题、文件路径、测试数量、工作流名称或依赖版本。不要使用「Full Changelog」作为主要内容。若需要给自己留一份提交对照，可以把比较链接放在校验段之后，并明确这是开发记录，而不是产品说明。

安装步骤面向没有使用过命令行的人，建议写成：

1. 下载并解压 `ricoh-mac-vX.Y.Z-macos-arm64.zip`。
2. 把 `ricoh-mac.app` 拖入「应用程序」文件夹。
3. 第一次打开时，按住 Control 键点按该应用，再选择「打开」。本应用使用个人签名，未经 Apple 公证，系统可能会提示无法验证开发者。选择「打开」即可继续。

不要把 `xattr` 命令放在主要步骤里。若仍需保留给熟悉终端的人，放到安装段末尾的一句说明即可。

校验段放在最后，标题可用「校验（可选）」。只给出文件名和 SHA-256，不再在安装段重复一遍。

发布标题建议改为「Ricoh Mac vX.Y.Z」，或在确定正式产品名后再统一替换。

## 每个版本如何撰写

在仓库中为每个版本保留一对说明文件：

- `docs/releases/vX.Y.Z.zh-CN.md`
- `docs/releases/vX.Y.Z.en.md`

文件只写「本版本更新」，不写安装步骤和校验值。安装段继续由模板生成，校验值由工作流在打包后填入。这样说明文字可以随版本一起被审查，而不会把每次构建才知道的哈希值写进仓库。

发版工作流改为读取这对文件，再拼接安装模板和校验段。若对应版本的说明文件缺失，发版作业应失败，以免再次发布出只有安装说明、没有功能更新的页面。

撰写规则：

- 用条目说明使用者能做什么，或界面看起来有什么变化。
- 中英文分开维护，含义一致，不要机器直译残留。
- 沿用应用里已经产品化的用语，例如「照片」「设备」「保存位置」「网络名称」。
- 上一版本已经包含、本版本只是继续提供的能力，可以各用一句交代，不要写成新功能。例如 v0.2.0 可以提到应用已内嵌 ChillDINGothic 字体，并注明这一项始于 v0.1.1。

`docs/releases/v0.2.0.zh-CN.md` 与 `docs/releases/v0.2.0.en.md` 作为后续版本的模板保留。已发布的 v0.2.0 GitHub Release 页面不按新格式重写。新的页面格式从下一个版本开始使用。

## 已确认的事项

2026 年 11 月 15 日（Asia/Shanghai）确认：

- 新的产品化发布页格式从下一个版本开始使用。
- 已发布的 v0.2.0 GitHub Release 页面不重写。
- `docs/releases/v0.2.0.zh-CN.md` 与 `docs/releases/v0.2.0.en.md` 作为后续发版的模板保留。

## 仍需决定的事项

- 发布标题使用「Ricoh Mac」，还是继续使用当前的应用文件名。
- 是否在说明末尾保留指向提交比较的链接。
